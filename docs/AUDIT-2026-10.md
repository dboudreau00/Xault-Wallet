# XaultWallet — code review & security audit (October 2026)

**Scope:** the whole repository at `eca14bd` (`main`): `src/`, `tests/`, `tools/`, build scripts, and
the security claims made in `README.md`, `SECURITY.md` and `PUBLIC-API.md`.
**Result:** 36 findings. The first pass found 20 (2 critical, 4 high, 7 medium, 6 low, 1
informational). A second, adversarial pass over those fixes found 9 more (XW-21–XW-29: 1 high,
3 medium, 4 low, 1 informational), including one where the first fix itself failed open. Smoke-testing
the release build found one more (XW-30, low). A third pass drove the whole product end to end, on
Windows through the released executable, and found five more (XW-31–XW-35: 1 medium, 3 low,
1 informational). A fourth pass, building 0.5, found one more in shipped code (XW-36, medium),
records the upstream behaviour and design decisions that shaped 0.5, and lists what a review of 0.5
found in its own new code before release, all fixed before it shipped (see
[Fourth pass](#fourth-pass-050)). All 36 are fixed on this branch. Every fix but XW-28 has a test that fails on the
old behaviour (XW-28 is explained where it's listed). Residual risks are listed at the end.

> This is an engineering review, not a substitute for the independent professional audit the project
> already calls for. It did not review Monero itself, monero-wallet-rpc, or third-party packages.

## How it was verified

Claims were checked against the running software rather than argued from reading alone:

- **Real Monero binaries.** `monero-wallet-rpc` / `monerod` **v0.18.3.1** (Ubuntu 24.04 `universe`
  package, built from the same upstream source as the official release; the sandbox's network policy
  blocked getmonero.org) driving a **private regtest chain** (`monerod --regtest --offline
  --fixed-difficulty 1`), so real wallets could be created, funded by mining, and spent.
- **Real UI rendering.** Every screen rendered headlessly with Avalonia 11.1.3 + Skia (the new
  `tools/UiSnapshots`), and the culture bug reproduced in a headless Avalonia harness.
- **Tests first.** Each finding has a unit or integration test that reproduces it; 209 unit tests
  and 10 regtest integration tests pass. CI runs both, plus the UI smoke test, on every push.
- **Tests that bite.** For the second-pass fixes, each fix was reverted in turn and its test was
  confirmed to fail. With the ownership gate disabled, for example, the regtest impostor test
  completes the restore against the impostor, i.e. the seed reaches it.
- **Upstream constants from upstream.** The chain-height estimate (XW-24) was ported from monero's
  own source (`master` @ `160e215`, 2026-10-02), not from memory.

Not executed in the first two passes: the Windows-only code paths (kill-on-close job object,
`GetExtendedTcpTable`), reviewed by hand and exercised by the Windows CI job, and macOS. The third pass
ran the released Windows executable end to end (see [Third pass](#third-pass-end-to-end-testing));
macOS is still only built, not run.

## What was already right

Worth saying plainly, because most of the architecture holds up:

- AES-256-GCM is used correctly: per-slot random salt, fresh 96-bit random nonce per seal, slot index
  bound into the AAD, auth-tag failure as the only "wrong password" signal, no plaintext comparisons.
- Argon2id parameters are strong by default and **bounded on load**, so a malicious header can't force
  a multi-gigabyte allocation. Tampering with the (unauthenticated) KDF header can only cause a failed
  unlock, never a downgrade, because a different key fails the tag.
- Unlock does constant work across both slots; slot position is randomised; the unused slot is
  indistinguishable random filler; writes are atomic (temp + fsync + replace).
- The send flow builds and signs first (`do_not_relay`) and broadcasts the exact transaction the user
  confirmed. Imports echo the derived address before sealing. The seed-offset policy is sound.
- The kill-on-close job object, the orphaned-temp-dir sweep, clipboard auto-clear and secret
  redaction show a security-minded author. The findings below are mostly about the edges.

## Findings

### XW-01
**Critical — wallet RPC unauthenticated for the whole unlocked session.**
`MoneroProcessManager` launched `monero-wallet-rpc --disable-rpc-login`, on the stated assumption that
loopback binding is enough and the server lives "for a few seconds". It actually lives for the whole
unlocked session, and loopback is reachable from the user's browser.

*Evidence (reproduced):* against a child launched with the app's exact flags, a request a web page can
send without a CORS preflight — `POST /json_rpc`, `Content-Type: text/plain`, `Host: evil.example` —
executed `create_wallet` and then **`query_key` returned the 25-word seed**. The server does not check
`Host` (DNS rebinding can read responses) and processes `text/plain` bodies (blind CSRF of `transfer` /
`sweep_all` works without reading anything). Any local process or user could drive it too.

*Fix:* per-session random HTTP Digest credentials. They are passed through a `0600` `--config-file`
inside a `0700` session directory, not argv, which other users can read via `/proc/<pid>/cmdline`, and
shredded once the server is up. The client sends credentials only for the `Digest` scheme, never Basic,
and never through a system proxy. The code's reason for disabling login ("digest + POST body can't
replay") was tested and is false on .NET 8: three consecutive digest-authenticated POSTs returned 200.
*Verified by:* `Backend_Rejects_Unauthenticated_And_Cross_Origin_Requests` (that exact request now
gets 401); `Session_Artifacts_Stay_Inside_The_Shredded_Directory` (no password in argv, dir mode 0700).

### XW-02
**Critical — the decoy's own payload proves a hidden wallet exists.**
The JSON sealed in each slot carried `"kind"` (`0` real / `1` duress), a label (`"Main"` vs
`"Wallet"`) and `"duressWipeReal"`. The duress feature exists for the case where an adversary holds the
device **and** the duress password. The vault format is public, so decrypting the decoy slot and reading
`"kind":1` is a few lines of code. README's "no flags, no metadata" was not true.

*Fix:* payload v2 — one identical field set for every slot (`v, network, mnemonic, seedOffset,
restoreHeight, daemonAddress, ephemeralWalletPassword, wipeOther`), no kind, no label. `WalletSecrets`
and `UnlockResult` no longer carry a real/decoy notion at all. v1 slots still open and are re-sealed as
v2 the first time their password is used (a slot can only be migrated with its own password; see
XW-22 for what that means for existing decoys).
*Verified by:* `DeniabilityTests` — decrypts slots exactly as an examiner would and asserts the decoy's
field list equals a single-wallet vault's; legacy-migration tests use byte-for-byte v1 payloads.

### XW-03
**High — "Change password" announced the real wallet.**
After unlocking with the duress password, Settings → Change password with that same password replied
*"That current password didn't unlock the real wallet."* — on screen, to whoever is coercing.

*Fix:* `ChangePassword` is now symmetric, like change-node: it re-seals whichever slot the password
opens, with neutral wording. It still refuses a new password that would open the other slot.
*Verified by:* `ChangePassword_Is_Symmetric_And_Only_Touches_The_Opened_Slot`.

### XW-04
**High — the send amount depended on the OS locale.**
The amount box was bound to a `decimal`, converted with the current culture, which accepts the group
separator. Reproduced in a headless Avalonia 11.1.3 harness: **en-US `0,25` → 25 XMR, `1,5` → 15 XMR;
de-DE `0.5` → 5 XMR; fr-FR `0.5` → 0**. The confirm dialog showed the wrong amount, which is the
only thing between a typo and an irreversible over-send.

*Fix:* `XmrAmount.TryParse`. `.` or `,` is always the decimal point and never a thousands separator,
so ambiguous input can only parse *lower* than intended. Live read-back (`= 0.25 XMR`) flags
thousands-looking input, and all amounts display culture-invariantly.
*Verified by:* `XmrAmountTests` (the exact inputs above, under six cultures).

### XW-05
**High — generated wallets rescanned the whole chain on every unlock.**
A generated seed's restore height came from wallet-rpc's `get_height` immediately after
`create_wallet`. That reports the wallet's local chain, which is **1**, not the tip; reproduced with
the tip at 301. Because the app restores from seed on every unlock, every unlock of a "new" wallet
scanned from genesis. That's slow on test networks and hours on mainnet through a remote node. README
claimed "first sync is fast".

*Fix:* read the **daemon's** tip *before* the seed exists, minus a 720-block margin (0 = full scan if
the node is unreachable). The same margin applies to "scan from now". (XW-24 then caps the node's
claim by the clock.)
*Verified by:* `Generated_Seed_Restore_Height_Tracks_The_Daemon_Tip` (against a chain grown past the margin).

### XW-06
**High — wipe-on-duress left the real wallet on the device.**
Settings → Restore keeps the replaced vault as `vault.xv.replaced-<time>` ("never destroyed"). A
duress wipe overwrote only `vault.xv`, so the real slot survived in those copies, contrary to the
"permanently, on that device" promise.

*Fix:* a wipe now also shreds `vault.xv.replaced-*`. The wipe fires on **any** use of the duress
password (unlock, change password, change node), and the survivor is re-sealed with the flag cleared
using the key already derived. So a duress unlock costs no extra Argon2 time and leaves a vault that
looks like a single-wallet one.
*Verified by:* `Duress_Wipe_Destroys_Replaced_Vault_Copies_Left_By_Restore`,
`Wipe_Fires_When_The_Duress_Password_Is_Used_To_Change_A_Password` (and `…_Change_The_Node`),
`Wipe_Reseals_With_The_Already_Derived_Key`.

### XW-07
**Medium — History showed 0 XMR for every transaction.**
`DataGridTextColumn` bindings are TwoWay. With the one-way XMR converter, `ConvertBack` threw on every
row (8 binding errors in the smoke test) and the cells rendered `0`.
*Fix:* a purpose-built history list (`HistoryRow`) with plain one-way display strings.
*Verified by:* the UI smoke test, which now fails on any binding error.

### XW-08
**Medium — addresses could display differently from their text.**
`SelectableTextBlock` didn't match the `TextBlock.mono` style, so addresses fell back to Inter, whose
contextual alternates render an `x` between digits as `×` (`…BUP2x2Uim…` displayed as `2×2`). The
same happened in the original app wherever an address used the default font.
*Fix:* `:is(TextBlock).mono` covers every address, txid and key, which render in Cascadia Mono or Consolas.
*Verified by:* rendered output inspected; the QR round-trip check decodes the Receive QR and requires
it to equal the displayed address URI.

### XW-09
**Medium — wallet-rpc wrote persistent files outside the shredded directory.**
With no `--log-file`, wallet-rpc wrote `monero-wallet-rpc.log` to the process working directory. Every
seed restore adds a ~280-line timestamped burst, so vault creation with an imported real and decoy seed
leaves two bursts seconds apart. It also created `~/.shared-ringdb`, which grew from 12 KB to 36 KB on
a single send. Both outlived lock, exit and duress wipe.
*Fix:* `--log-file` and `--shared-ringdb-dir` inside the session directory; `WorkingDirectory` set there too.
*Verified by:* `Session_Artifacts_Stay_Inside_The_Shredded_Directory`.

### XW-10
**Medium — the app's own log could tell the wallets apart.**
`xaultwallet.log` persists and survives a wipe. It recorded `"syncing against <node> from height <N>"`
on every unlock (the restore height is unique per seed) and "Transfer submitted" on every send, which
can be checked against the decoy's on-chain history. RPC exception messages, which are logged, also
embedded the (redacted) request body, including restore heights and destination addresses.
*Fix:* those lines are removed. Exception messages carry only the method and the backend's error;
the redacted body moves to `MoneroRpcException.Diagnostics`, which is never logged.

### XW-11
**Medium — "Fetch key from wallet" never worked.**
`get_tx_key` answers `{"tx_key": …}`, but the code read it through the `{"key": …}` DTO used by
`query_key`, so every lookup produced an empty key with no error. *Found by the new integration test.*
*Fix:* a dedicated `GetTxKeyResult`, and an empty key now throws. *Verified by:* the regtest funds-flow test.

### XW-12
**Medium — port-hijack race.**
The child's port is chosen, released, then passed on its command line, which other users can read. A
process that binds it first makes the child fail to bind and receives `restore_deterministic_wallet`,
seed included. Digest auth doesn't help: it authenticates only the client, and monero sends no `rspauth`.
*Fix:* before any secret is sent, verify that every listener on the port belongs to the child: `/proc`
on Linux, `GetExtendedTcpTable` on Windows. A 401 during readiness is now a hard failure.
*Residual:* macOS has no equivalent check here; there the risk is the pre-existing one.
*Verified by:* `LoopbackPortOwnershipTests` (own listener, foreign PID, closed port). **The first version
of this fix failed open; see XW-21.**

### XW-13
**Medium — mainnet by default.** First-run defaults were mainnet and `127.0.0.1:18081` in an app whose
README says not to use real funds. *Fix:* Stagenet by default; mainnet stays one click away behind its
red warning (now also a red "MAINNET · REAL FUNDS" pill on the wallet screen).

### XW-14
**Low — PATH auto-detect.** A blank binary path fell back to the bare name `monero-wallet-rpc`, but the
launcher requires `File.Exists`, which is false for bare names. "Test binary" (via `Process.Start`) passed
while unlocking failed. *Fix:* `ExecutableLocator` resolves PATH to an absolute path and skips relative
PATH entries. *Verified by:* `ExecutableLocatorTests`. (XW-25 closes the remaining relative-path case.)

### XW-15
**Low — guessable passwords.** Only "8+ characters" was enforced; `password`, `12345678`,
`Password123!` and `qwertyuiop` were accepted for a file that can be attacked offline. *Fix:* the estimator
discounts repeats, sequences, keyboard runs and the most common passwords, and *Very weak* is refused
for main, duress and changed passwords. Still a heuristic; zxcvbn would be better.

### XW-16
**Low — redaction gaps.** `sweep_all`'s `tx_key_list` / `tx_metadata_list` (and other `*_list` /
txset fields) weren't redacted, and the stderr tail, which reaches exceptions and the log, wasn't
scrubbed. *Fix:* keys added, and the stderr tail masks address-length base58 and 64-hex strings.

### XW-17
**Low — the bundled font was never used.** The window asked for the family name `Inter` (a system
lookup), so Linux fell back to DejaVu. *Fix:* reference the embedded `fonts:Inter#Inter`.

### XW-18
**Low — restore height input.** The import "specific block" box was a culture-bound `ulong`; `2.800.000`
on de-DE failed to bind and silently left 0. *Fix:* `BlockHeight.TryParse`, culture-independent.
(The first version accepted *any* grouping; see XW-26.)

### XW-19
**Low — silent second launch.** A second instance exited with code 2 and no feedback. *Fix:* on
Windows it signals the running instance, which restores and focuses its window.

### XW-20
**Info — daemon probe route.** Without a SOCKS proxy the app's own daemon probe used the system or
environment proxy, while wallet-rpc connects directly. *Fix:* the probe takes wallet-rpc's route.

## Second pass

An independent adversarial review of the first-pass fixes, re-verified the same way.

### XW-21
**High — the port-ownership check failed open.**
XW-12's check returned *"can't tell"* whenever reading the tables threw, and *"can't tell"* was
treated as *"fine"*. In the hijack, the child loses the port and **exits**. Once it is reaped, its
`/proc/<pid>/fd` is gone, enumeration throws, and the check passes. An impostor that answers at once was
refused, because the child was still alive. An impostor that simply **holds its first answer until the
child is gone** was not. Reproduced against the pre-fix commit (`bad2684`): that impostor received
`get_version`, then `restore_deterministic_wallet` carrying the `seed` and the wallet password.
Two smaller gaps: the check didn't run before `create_wallet`, so an impostor could hand out a seed it
knows. And on Windows, a same-port listener on an unrelated interface made the check refuse a
legitimate backend.
*Fix:* fail closed. A vanished process owns nothing, and on Linux/Windows only a definite *yes* passes
(`LoopbackPortOwnership.IsTrusted`). `MoneroProcessManager.EnsureBackendIsOurs()` also requires the child
to be alive, and runs at readiness, before `restore_deterministic_wallet` and before `create_wallet`.
Windows only considers `127.0.0.1` and wildcard listeners.
*Verified by:* `A_Process_That_Has_Exited_Owns_Nothing`, `Only_A_Definite_Yes_Is_Trusted…`, and the
regtest test `Seed_Is_Never_Sent_To_An_Impostor_Holding_The_Backend_Port`. That test binds the port
before the real `monero-wallet-rpc` and answers like a server, in two variants. The prompt impostor is
refused with *"Another program is answering…"*. The patient one is refused with *"monero-wallet-rpc is
not running"*. Both stop after one `get_version`, and neither ever receives the seed. Run unchanged
against `bad2684`, the patient variant fails as described above.

### XW-22
**Medium — upgraded 0.1 vaults keep the decoy marker until the decoy is used.**
A slot can only be re-sealed by its own password. After a 0.1 user unlocks with the main password, the
decoy slot still holds `"kind":1` inside its encryption, which is XW-02's leak. Using the duress password
converts it, but with 0.1's wipe-on-duress enabled it also wipes the main wallet. Nothing told the user any of this.
*Fix (mitigation, the format can't be fixed from the other slot):* `UnlockResult.UpgradedFromLegacyFormat`
triggers a one-time notice. It is deliberately **symmetric**: it is shown for *either* slot of a 0.1 vault.
A notice only for 0.1 "main" slots would make the first decoy unlock after upgrading look different.
`SECURITY.md` → *Upgrading from 0.1* explains the exposure and gives a rebuild procedure.
*Verified by:* `Upgrade_Is_Reported_Once_And_Identically_For_Either_Slot` (both slots, true then false),
`A_Current_Format_Vault_Never_Reports_An_Upgrade`, and the `wallet-upgraded` UI snapshot.

### XW-23
**Medium — files created world-readable.**
Everything was written with the process umask. With the common `022`, that means `0644` files in a
`0755` folder: the vault (offline-attackable), the logs and, worst, the optional **plaintext seed
backup**. Whether another account could actually read them came down to the permissions of the parent
folders. The app relied on those instead of setting its own.
*Fix:* `PrivateFiles`. The data and log folders are `0700`, and the vault, settings, logs, temp files,
restored vaults and exports are `0600`. Files are created with that mode, and an existing file is
tightened *before* anything is written into it. At startup, folders made by older versions are swept
(symlinks are neither followed nor changed). Save-dialog files (seed backup, history CSV) are written
by the app as `0600` whenever the dialog yields a local path. Windows relies on the profile ACLs.
*Verified by:* `PrivateFilesTests` under umask `022`, including the real vault write and the logger.

### XW-24
**Medium — a node's height became a new seed's restore height unchecked.**
XW-05 made a new seed start at the node's tip minus 720 blocks. A lying or broken node claiming a
far-future height pushed that start above the real chain. The height is sealed in the vault, so the
payments that followed would stay invisible even after switching to an honest node.
*Fix:* `RestoreHeights.ForNewSeed` takes `min(node tip, clock estimate) − 720`. The estimate is
monero's own `wallet2::get_approximate_blockchain_height`, ported from upstream `master` (latest hard
fork's height and time, 120 s per block, minus a per-network correction). Taking the lower value can
only cost extra scanning.
*Verified by:* `RestoreHeightTests` (upstream values hand-computed for all three networks, a 99,999,999
claim capped, regtest-sized chains passed through) and `Generated_Seed_Restore_Height_Tracks_The_Daemon_Tip`.
*Residual:* if the estimate itself runs ahead of the real chain, a lying node can still push the start
past the tip by that lead minus 720 blocks.

### XW-25
**Low — a relative binary path could run a file from the current directory.**
The launcher accepted any path for which `File.Exists` was true, and `File.Exists` resolves relative
names against the current directory. `Process.Start` then searches the app's folder, the current
directory and `PATH`. A bare name in Settings, or the old fallback when auto-detect found nothing, could
therefore start a planted `monero-wallet-rpc` from wherever the app was launched, and that process
receives the seed.
*Fix:* `ExecutableLocator.EnsureLaunchable` refuses anything not fully qualified, in both the launcher
and "Test binary". Bare names typed in Settings resolve on `PATH` (`ResolveConfigured`). Auto-detect
returns *nothing found* instead of a bare name.
*Verified by:* `A_Relative_Name_Is_Never_Launched_Even_When_The_File_Is_Right_There` (the planted file
exists in the current directory) and the `ResolveConfigured` tests.

### XW-26
**Low — height parsing too lenient.**
XW-18's parser stripped every separator, so `3150000.0` became **31,500,000**, and `31,50,000` or
`3,150.000` were accepted. A restore height that's too high hides payments.
*Fix:* plain digits, or groups of exactly three behind one kind of separator. Everything else is refused.
*Verified by:* `BlockHeightTests` (the inputs above, plus `3'150'000` and `1,000` still accepted).

### XW-27
**Low — history row stuck at "9/10 confirmations".**
To keep the scroll position, history redraws only while a row is still confirming. That was judged at
the *new* height, so the block that settles a row was exactly the one that skipped the redraw.
*Fix:* judge at the old height (`OnHeightChanged(oldValue, newValue)`).
*Verified by:* the UI smoke test's history check (9 → 10 confirmations must redraw as settled). It fails
with the old condition.

### XW-28
**Low — key material left un-zeroed on a failure path.**
`VaultFile.TryOpen` derives a key for both slots. If slot 0 opened and slot 1's Argon2 derivation then
threw (e.g. out of memory), the opened payload and its key escaped every `using` block. `TryDecrypt` also
ran outside the `try`, so a throw there leaked that key.
*Fix:* everything for a slot runs inside its `try`, and a failure disposes an already-opened result.
*Not separately tested:* it would need fault injection into the KDF. The change is structural and
covered by the existing open/unlock tests.

### XW-29
**Info — `1,000 XMR` skipped the read-back hint.**
`TryParse` accepted the `XMR` suffix but `LooksThousandsGrouped` didn't, so that input showed no
*"did you mean thousands?"* note. *Fix:* same suffix handling. *Verified by:* `XmrAmountTests`.

## Release smoke test

Before tagging, the exact `release.yml` publish command was run for all three targets with the SDK the
CI runner uses. Each output is one self-contained file with no stray native libraries. The Linux binary
was then launched for real under Xvfb with an empty home directory.

### XW-30
**Low — without `~/.config`, the vault went to the current directory (Linux).**
The data folder came from `Environment.GetFolderPath(SpecialFolder.ApplicationData)`. With the default
option, that returns **an empty string when the folder doesn't exist**. `Path.Combine("", "XaultWallet")`
is then relative, so the vault, settings and logs were created in, and only found from, whatever
directory the app was started in. Started from another directory, the vault seemed to vanish and the
app offered to create a new one. Started where the directory wasn't writable, it failed. On Linux the
folder is `~/.config`, which desktop sessions normally create but a fresh account, a minimal install or
a container may lack. macOS and Windows aren't affected in practice. Since .NET 8, macOS maps it to
`~/Library/Application Support` ([documented breaking change](https://learn.microsoft.com/dotnet/core/compatibility/core-libraries/8.0/getfolderpath-unix)),
and that folder always exists, as `%APPDATA%` does on Windows.
*Fix:* `SpecialFolderOption.DoNotVerify`, and the root must be fully qualified or startup stops with
a clear error. *Verified by:* the UI smoke test's data-folder check, which uses a config root that
doesn't exist yet. With the old call it fails (`Data folder is 'XaultWallet'`) and leaves a stray
folder in the working directory. Also the republished binary: `~/.config/XaultWallet` was created
`0700`, and nothing was written where it was launched.

## Third pass: end-to-end testing

The product was driven end to end the way a person uses it, by one scenario with two drivers:

- **Windows, the released executable** (`.github/workflows/e2e-windows.yml`). The exact `win-x64`
  zip, the official Monero CLI **v0.18.5.1** for Windows (`hashes.txt` verified against binaryFate's
  key, the zip against `hashes.txt`) and a private regtest chain on `windows-latest`. The app is driven
  from outside through Windows UI Automation (`tests/XaultWallet.E2E.Windows`, FlaUI): create a vault,
  verify the seed backup, duress password and decoy, unlock both wallets, receive, copy the address,
  send 12.5 XMR with the confirmation checked line by line, History, the decoy receiving it, Settings.
  The app is then closed with its own close button, and the run fails if `monero-wallet-rpc` outlives
  it, a session folder is left in `%TEMP%`, or anything was written next to the exe. It passed: the app
  exited 0.3 s after Close with nothing left behind. The release workflow now requires this test on the
  zip it attaches.
- **Linux, in process** (`tests/XaultWallet.E2E.Headless`), with real pointer and keyboard input, so a
  covered or disabled button fails the click. It runs in CI against the Ubuntu-packaged v0.18.3.1.

Both drivers read the UI the way assistive technology does (Avalonia's automation peers, which back
the Windows UI Automation provider), which is how XW-32 and XW-33 surfaced. Screenshots of every step
were reviewed by eye, which is how XW-31 surfaced. The UI smoke test (`tools/UiSnapshots`) gained
checks for XW-32–XW-35, each confirmed to fail on the old code.

### XW-31
**Medium — mining rewards listed as outgoing payments.**
wallet-rpc reports coinbase outputs (solo mining, P2Pool payouts) with transfer type `block`. History
only treated `in` and `pool` as incoming, so every reward was drawn as a payment *sent*: orange arrow,
"−35.12 XMR", the raw title "block". It was also counted towards 10 confirmations, when mined coins
unlock after 60 (`CRYPTONOTE_MINED_MONEY_UNLOCK_WINDOW`), so a reward looked spendable 50 blocks early.
A miner reading History would see their income as spending.
*Fix:* `block` is incoming, titled "Mining reward", and confirms over 60 blocks
(`HistoryRow.ConfirmationsToUnlock`); the history redraw uses the same per-row window.
*Verified by:* the UI smoke test's mining-reward check (+0.6 XMR, "59/60", settled at 60) and the
end-to-end screenshots of a wallet holding 80 mined blocks.

### XW-32
**Low — password boxes readable through UI Automation.**
Avalonia's `TextBox` serves its full `Text` through the UI Automation Value pattern even when masked
with `PasswordChar`. Any process in the same desktop session could read the vault password, the
duress password, or a new password as it was typed, with no hooks or code injection. (WPF's
`PasswordBox` refuses this.) Same-session malware has other ways in (see SECURITY.md), so this is
defence in depth, but it was the cheapest of them.
*Fix:* `SecretTextBox`, used for all eight masked fields. Its automation peer accepts input (assistive
tools and the end-to-end test can type) and returns no value.
*Verified by:* the UI smoke test reads every filled password box's value through its automation peer
and fails if it gets the text (it does on a plain `TextBox`); the Windows end-to-end test types every
password through UI Automation and fails if one reads back.

### XW-33
**Low — screen readers got nothing for the balance.**
Avalonia 11.1's `TextBlock` peer always reports `Text` as its accessible name and ignores
`AutomationProperties.Name`; for text built from `Run`s, `Text` is null. The balance (two Runs: bright
whole part, dimmed fraction) was therefore announced as nothing. Buttons whose content is an icon plus
text were announced by their content's type name, "Avalonia.Controls.StackPanel": the title-bar
Settings button, backup export/restore, the folder buttons; also two node pickers, the "Verify a
payment" header and the number boxes' inner fields had no name at all.
*Fix:* `NamedTextBlock` (a TextBlock whose peer honours `AutomationProperties.Name`, falling back to
the Runs' text) for the balance and the other Run-based text; names for every flagged control;
template parts named through styles.
*Verified by:* the UI smoke test, on every screen, requires a real accessible name for every button,
check box, radio button, combo box, edit, tab, slider and spinner, and checks what the balance is
announced as (empty with a plain TextBlock).

### XW-34
**Low — an entrance animation could leave a screen permanently transparent.**
In Avalonia 11.1, an animation with `FillMode.Forward` that is torn down before its first frame
commits `default(T)` as a local value (`AnimationInstance.Unsubscribed` → `ApplyFinalFill`): opacity
0, for good. A style entrance that starts at opacity 0 can hit this when its style is re-applied early.
While adding motion, the Settings screen came up blank this way whenever it was not the first window
(measured: a section animated to 0.99996, then a second, never-stepped instance committed 0). The
startup screen's existing fade-ins used the same pattern, including the panel holding
"Continue anyway", the only way past the splash when no node answers.
*Fix:* no entrance is a style animation. `app:Entrance.Rise` / `app:Entrance.Fade` play them from code
when the element is attached: starting values are set before the first frame (no flash), and resting
values are restored in a `finally` (never stuck). The only style animations left loop forever, and
loops commit nothing.
*Verified by:* the UI smoke test fails if any element with an entrance is not at full opacity and at
rest once the screen has settled, on every screen; it measures an entrance frame by frame (starts at
0, moving at 0.88, ends at 1 and at rest) and a screen change (the new screen starts at 0.00 before its
first frame and ends opaque; the old one is hidden).

### XW-35
**Info — usability.**
- Copying the transaction ID or key from the Send tab's payment proof gave no feedback: the "copied"
  line only existed on the Receive and History tabs. Copy and export now confirm with one toast on
  whichever tab is open (checked by the end-to-end test).
- The window (1080×760, minimum 900×600) did not fit a 1366×768 laptop at 125 % scaling, which has
  about 570 px of usable height: the bottom of each screen was off-screen. The window now opens
  centred, shrinks to the screen's working area, has a 560 px minimum, and the send confirmation
  scrolls.
- Avalonia's `CrossFade`, used for screen changes, shows the new screen at full opacity for one frame
  before fading it in. The new transition starts it hidden (the smoke test measures 1.00 with CrossFade
  and 0.00 now).

## Fourth pass: 0.5.0

Scope: everything 0.5 adds — vault format 2 and open sessions, several wallets per password, wallets
restored from keys and watch-only, contacts, labels and notes, accounts and subaddresses,
multi-recipient sends, `monero:` links, message signatures and reserve proofs, and the
monero-wallet-rpc installer — plus how vaults from 0.1–0.3 are carried into it.

How it was verified:

- **Real Monero, real UI.** The end-to-end scenario grew a second act, run on Linux in process and on
  Windows against the released executable: add a second wallet (seed generated and checked), switch,
  save a contact, pay the contact and the second wallet in one transaction, see the second wallet
  receive, lock, reopen on the wallet used last, and check that the duress password still opens only
  the decoy (now paid twice, with no contacts). On Windows the scenario starts **without**
  monero-wallet-rpc and installs it with the app's own button, from getmonero.org, signature and
  checksum checked.
- **Regtest integration tests** against monero-wallet-rpc v0.18.3.1 for key and watch-only restores
  (including wrong keys), subaddresses and accounts surviving a lock, a two-subaddress transaction with
  its proofs, and changing the node of an open wallet.
- **Vault tests on genuine old files.** Format 1 files are built byte for byte the way 0.1–0.3 wrote
  them, then opened by 0.5 (which leaves them as they are), saved in their own format, refused a
  change that doesn't fit, and upgraded on request from either password — including a 0.3 decoy with
  wipe-on-duress.
- **The UI smoke test** renders 35 screens (every tab and sheet of the new wallet screen, the
  add-wallet flow, the vault-format card), decodes the payment-request QR code back to the exact link, and keeps the
  accessibility and password-privacy checks on every one. It also drives the behaviour the review
  below fixed through the real views (key presses, list bindings), each check confirmed to fail on
  the code before its fix.
- **Source, not memory.** Claims about monero-wallet-rpc are from its source (`wallet_rpc_server.cpp`
  and `wallet2.cpp` at v0.18.3.1, `electrum-words.cpp` at v0.18.4.0), then confirmed against the
  v0.18.3.1 binary.

### XW-36
**Medium — a subaddress could be handed to a second payer after a lock.**
0.2 and 0.3 keep only the seed: every unlock restores a fresh wallet, and monero-wallet-rpc numbers new
subaddresses after the last one *it knows*. A subaddress that was given out but not yet paid is not
known after a restore, so **New subaddress** handed out the same address again. Reproduced with
monero-wallet-rpc v0.18.3.1: two restores of one seed, `create_address` on each, both returned index 1
and the same address. Two payers who were each told "this address is yours alone" could be linked to
each other — the property the Receive tab promised.
*Fix:* the vault records, per account, how many subaddresses (and accounts) were handed out; opening a
wallet re-creates them before anything is shown, so the next one continues the numbering. Labels are
kept with them.
*Verified by:* `Subaddresses_And_Accounts_Handed_Out_Before_A_Lock_Come_Back` (regtest: five handed
out, the next is #5 and none of the old ones), and the vault round-trip tests.

### Upstream behaviour and decisions that shaped 0.5

These were found while building 0.5, before any of it shipped; they are recorded because each one
would have been a finding.

- **`generate_from_keys` doesn't check the keys against the address.** monero-wallet-rpc
  (`on_generate_from_keys`) only parses them; a wrong view key makes a watch-only wallet that
  silently never sees a payment, and a wrong spend key one that can never spend. `wallet2::load_keys`
  does check (`verify_keys`), so 0.5 closes the new wallet and opens it again, then names the wrong key
  with a watch-only probe. A first approach, `sign` with the view key, **crashed** monero-wallet-rpc on
  the Ubuntu build (a debug assertion on mismatched keys) and was dropped. Restoring from keys never
  reimplements the check: it is Monero's own code that accepts or refuses. Covered by
  `Wallets_Restored_From_Keys_And_Watch_Only_Have_The_Seeds_Address`.
- **Payment-link amounts are parsed strictly.** The app reads typed amounts with either `.` or `,` as
  the decimal point. Applied to a `monero:` link, `tx_amount=1,500` would have become 1.5 XMR — a
  thousandfold underpayment the user never typed. Links accept only digits with an optional `.` and at
  most 12 decimals; anything else is refused with a reason, as are links with a payment ID (obsolete,
  and a privacy leak) or several addresses.
- **A lock could cut a save short.** With an open session, saves run in the background; locking
  dropped the session key while a write could still be pending. Saves now serialize the profile on the
  UI thread when their turn comes and finish before the session closes (`VaultSession` serializes
  `Save`/`Dispose`; `ProfileViewModel` waits for its write queue).
- **Contacts and wallets are per password, and so is everything that changes them.** An open profile
  re-seals only its own slot; the other is written back byte for byte from disk, so a session never
  needs (or holds) the other password's key, and the same rules apply to both profiles.
- **Old vaults convert only when asked.** Converting a format 1 file can re-seal only the slot whose
  password is in hand; the other is carried byte for byte into its larger slot until its own password
  opens it. Every slot is tried in both layouts, so that costs no different work — but the holder of
  the carried slot's password can see it was carried. The first design converted on open; the review
  below caught what that tells an examiner, and the upgrade became a choice (see there).
- **The installer trusts one key, pinned.** `hashes.txt` must be clearsigned by binaryFate's key as it
  ships in Monero's repository, accepted only for its primary and signing-subkey fingerprints; the
  verifier refuses anything before or after the signed block, any header but `Hash`, and other key or
  signature types. Tested against the real v0.18.5.1 `hashes.txt` and against every tampering tried
  (`SignedReleaseListTests`); a Windows checkout's CRLF line endings broke one fixture until the test
  normalised them (the verifier itself canonicalises line endings, as RFC 4880 requires).

### Review of 0.5 before release

A review of the 0.5 code, before release, found these. None was in a released version; each would
have been a finding. Every test named below fails on the code before its fix.

- **Converting an old vault on open told the duress password's holder about the other one.** Opening
  a 0.2/0.3 vault converted it to format 2 at once, re-sealing the opened slot and carrying the other.
  The holder of the duress password and the file could then see that their slot was carried while the
  file had been converted — by the other password. *Fix:* a format 1 file stays format 1 (0.5 saves in
  it) until the user upgrades it in Settings, which explains the order that leaves nothing to see (the
  duress password first) and the alternative when that password wipes (rebuild). *Verified by:*
  `A_0_3_Vault_Opens_With_Either_Password_And_Is_Not_Rewritten`,
  `A_Save_Keeps_A_0_3_Vault_In_Its_Format_And_The_Other_Slot_As_It_Was`,
  `Upgrading_From_The_Decoy_First_Leaves_Its_Holder_Nothing_To_See`.
- **A duress wipe that failed to write was forgotten.** The wipe is silent by design, so a failed write
  left the main profile on disk with nothing to try again. *Fix:* it is applied by every later write
  until one succeeds. *Verified by:* `A_Duress_Wipe_That_Could_Not_Be_Written_Is_Applied_By_The_Next_Write`.
- **An open session could write into a different vault.** A save re-reads the file and re-seals its
  slot index: if the file had been replaced (a restore, another copy), it would have written into
  someone else's slot. *Fix:* the slot's salt must still be the session's. *Verified by:*
  `A_Session_Will_Not_Write_Into_A_Vault_That_Was_Replaced`.
- **The log could count wallets.** Per-wallet events ("wallet added", a backend starting) were logged
  each time, so the log of a session differed with the number of wallets a profile has. *Fix:* those
  lines are gone or written at most once per run. *Verified by:* reading every call site.
- **A wallet that had handed out more than 64 subaddresses in an account wouldn't open** with
  monero-wallet-rpc up to v0.18.4.2, whose `create_address` takes at most 64 at a time. *Fix:* batches
  of 64. *Verified by:* `A_Wallet_That_Handed_Out_Many_Subaddresses_Still_Opens` (regtest, 150).
- **Re-checking spent outputs told a remote node every key image of the wallet**, and changing the node
  dropped the trust monero-wallet-rpc gives a local one. *Fix:* the re-check is only offered, and only
  runs, with a node on this computer, which stays trusted. *Verified by:*
  `Spent_Outputs_Are_Rechecked_Only_With_A_Node_On_This_Computer` (regtest).
- **Editing a contact didn't reach a send form already paying it** — in another open wallet, or in the
  same one once the list re-sorted (a list that moves its selected item drops it) — and *Pay* on a
  contact already picked kept the old address. *Fix:* forms follow the contact, a confirmation built for
  its old address is withdrawn, and *Pay* always re-applies. *Verified by:* the UI check
  `CheckContactEditsReachSendForms`.
- **The seed could appear after the Manage sheet closed.** Revealing it waits for the password check
  and for wallet-rpc; closing the sheet meanwhile didn't stop it, and the next opening showed the seed
  without the password. *Fix:* the reveal is dropped if the sheet closed or the secrets were hidden in
  the meantime, and the sheet always opens with them hidden. *Verified by:* `CheckManageOpensWithSecretsHidden`
  and reading the guard.
- **Two removals could leave a profile with no wallet**, which can't be opened: the "last wallet" check
  ran before the password check, not after. *Fix:* checked again after it. *Verified by:* reading.
- **Locking left the wallets on screen and usable** while their backends stopped, and a change saved
  then reported success though the session had closed. *Fix:* the screen leaves at once, the next
  unlock (and a backup restore) waits for the lock to finish, and a save that comes too late fails.
  *Verified by:* the end-to-end scenarios (every lock, then unlock) and reading.
- **Seed generation and import checks outlived a lock or exit**, each with its own monero-wallet-rpc.
  *Fix:* a lock cancels those of the add-wallet screen, exit cancels all, and both wait for the
  backend to stop. *Verified by:* `CheckTemporaryBackendsEnd`.
- **Arrow keys or the mouse wheel on the closed wallet switcher started every wallet on the way**
  (choosing a wallet starts its monero-wallet-rpc). *Fix:* they open the list; Enter or a click
  chooses. *Verified by:* `CheckSwitcherKeysOpenTheList`, with real key presses.
- **Hiding amounts covered one wallet only**: switching showed the next one's balance, and the account
  picker kept its figures. *Fix:* one setting, applied to every open wallet and the picker at once.
  *Verified by:* `CheckHideAmountsEverywhere`.
- **A note being typed was lost** whenever the history list was rebuilt (as each block arrives).
  *Fix:* the open row keeps its draft. *Verified by:* `CheckNoteDraftSurvivesRebuild`.
- **The same wallet could be added twice** by its keys or watch-only, when its seed version hadn't been
  opened that session (a seed wallet's address wasn't kept). Two entries for one wallet count their
  subaddresses separately — XW-36 again. *Fix:* the address is kept once known. *Verified by:*
  `CheckSameWalletIsRecognised`.
- **Another account's first address was called "Main address".** It is a subaddress (8… on mainnet).
  *Fix:* it is the account's address. *Verified by:* `CheckAccountAddressTitles`.

## Residual risks (documented, not fixed)

- **Wipe flag before it fires.** An examiner who decrypts the decoy *offline*, without the app ever
  opening it, can see `wipeOther: true` and infer a second wallet. That's inherent: the instruction must
  be readable with the duress password. Without wipe-on-duress, the decoy is indistinguishable.
- **Multiple snapshots of the vault file** taken over time reveal which slots changed. If both changed,
  two live wallets exist. This is the same limitation as hidden volumes.
- **Every unlock rescans from the restore height.** Only the seed persists, which is a design choice.
  Old wallets on mainnet will sync slowly on every unlock. Advancing the stored height past spent
  history, or an opt-in encrypted cache, would fix it at a privacy cost.
- **Managed memory and SSD shredding** remain best-effort (unchanged; see SECURITY.md).
- **macOS:** no port-ownership check (XW-12/XW-21); the per-session digest credentials remain.
- **0.1 vaults and their copies** keep the decoy marker until the decoy is used or the vault is rebuilt
  (XW-22). Copies made before upgrading keep it forever.
- **Restore-height cap** is only as good as the clock estimate (XW-24).
- **Release binaries are unsigned.** The release workflow publishes SHA256SUMS; code signing needs a certificate.
- **What is on screen is readable by other programs in your session** (screen capture, or UI Automation
  for visible text such as the seed words while they are shown, addresses and balances). Only masked
  password boxes are withheld (XW-32). As SECURITY.md says, a compromised session defeats any wallet.
- **Reduce-motion** is read from Windows only (plus `XAULTWALLET_REDUCE_MOTION`); macOS's and GNOME's
  settings are not consulted yet.
- **The macOS build is not run end to end** in CI; Windows (the released exe) and Linux are.
- **Several wallets on one remote node** can be linked by the node's operator (same IP, same times).
  Your own node or a SOCKS proxy avoids it (SECURITY.md).
- **Watch-only wallets can't see spends** without key images from the full wallet, which 0.5 doesn't
  import; their figure is labelled *received*, not balance.
- **The vault holds 256 KiB per password** (4 KiB in a 0.2/0.3 vault until it is upgraded). Ample for
  hundreds of wallets and contacts, but finite: a change that doesn't fit is refused, never truncated.
- **Going back to 0.3 needs a backup.** 0.3 can't open an upgraded vault, nor a password's part that
  0.5 has saved.
- **A vault from 0.3 shows which of its passwords have been used in 0.5** — each to the holder of that
  password (its part is still in 0.3's layout, or carried by an upgrade). Using the duress password
  in 0.5 first avoids it; with wipe-on-duress, rebuilding the vault does (SECURITY.md).
- **The installer is as trustworthy as the key copy inside the release** that runs it (and that key).
  Bringing your own verified monero-wallet-rpc remains the recommendation.
- **No independent audit yet** of the vault format or of the Konscious Argon2 implementation.

## Recommendations, in priority order

1. Commission the professional third-party audit before any mainnet story, as the README already says.
2. Sign release binaries (Authenticode, Apple notarisation) and pursue reproducible builds.
3. Restore-height advancement (or an opt-in encrypted wallet cache) to make old wallets unlock fast.
4. Exclude the window from screen capture while the seed is shown (`SetWindowDisplayAffinity`).
5. Replace the strength heuristic with zxcvbn, and add an optional keyfile second factor.
6. Built-in Tor (`--proxy` + `.onion` nodes) with a clear UI toggle, since the SOCKS plumbing already exists.
7. Key-image import for watch-only wallets, so they can show spends (and offline signing with it).
