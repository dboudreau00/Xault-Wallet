# XaultWallet — code review & security audit (October 2026)

**Scope:** the whole repository at `eca14bd` (`main`): `src/`, `tests/`, `tools/`, build scripts, and
the security claims made in `README.md`, `SECURITY.md` and `PUBLIC-API.md`.
**Result:** 29 findings in two passes. The first pass found 20 (2 critical, 4 high, 7 medium, 6 low,
1 informational). A second, adversarial pass over those fixes found 9 more (XW-21–XW-29: 1 high,
3 medium, 4 low, 1 informational), including one where the first fix itself failed open. All 29 are
fixed on this branch. Every fix but XW-28 has a test that fails on the old behaviour (XW-28 is
explained where it's listed). Residual risks are listed at the end.

> This is an engineering review, not a substitute for the independent professional audit the project
> already calls for. It did not review Monero itself, monero-wallet-rpc, or third-party packages.

## How it was verified

Claims were checked against the running software rather than argued from reading alone:

- **Real Monero binaries.** `monero-wallet-rpc` / `monerod` **v0.18.3.1** (Ubuntu 24.04 `universe`
  package, built from the same upstream source as the official release; the sandbox's network policy
  blocked getmonero.org) driving a **private regtest chain** (`monerod --regtest --offline
  --fixed-difficulty 1`), so real wallets could be created, funded by mining, and spent.
- **Real UI rendering.** Every screen rendered headlessly with Avalonia 11.1.3 + Skia (the new
  `tools/UiSnapshots`), and the culture bug reproduced in a headless Avalonia harness.
- **Tests first.** Each finding has a unit or integration test that reproduces it; 207 unit tests
  and 10 regtest integration tests pass. CI runs both, plus the UI smoke test, on every push.
- **Tests that bite.** For the second-pass fixes, each fix was reverted in turn and its test was
  confirmed to fail. With the ownership gate disabled, for example, the regtest impostor test
  completes the restore against the impostor, i.e. the seed reaches it.
- **Upstream constants from upstream.** The chain-height estimate (XW-24) was ported from monero's
  own source (`master` @ `160e215`, 2026-10-02), not from memory.

Not executed here: the Windows-only code paths (kill-on-close job object, `GetExtendedTcpTable`) —
reviewed by hand and exercised by the Windows CI job — and macOS.

## What was already right

Worth saying plainly, because most of the architecture holds up:

- AES-256-GCM is used correctly: per-slot random salt, fresh 96-bit random nonce per seal, slot index
  bound into the AAD, auth-tag failure as the only "wrong password" signal, no plaintext comparisons.
- Argon2id parameters are strong by default and **bounded on load**, so a malicious header can't force
  a multi-gigabyte allocation. Tampering with the (unauthenticated) KDF header can only cause a failed
  unlock, never a downgrade, because a different key fails the tag.
- Unlock does constant work across both slots; slot position is randomised; the unused slot is
  indistinguishable random filler; writes are atomic (temp + fsync + replace).
- The send flow builds and signs first (`do_not_relay`) and broadcasts the exact transaction the user
  confirmed. Imports echo the derived address before sealing. The seed-offset policy is sound.
- The kill-on-close job object, the orphaned-temp-dir sweep, clipboard auto-clear and secret
  redaction show a security-minded author. The findings below are mostly about the edges.

## Findings

### XW-01
**Critical — wallet RPC unauthenticated for the whole unlocked session.**
`MoneroProcessManager` launched `monero-wallet-rpc --disable-rpc-login`, on the stated assumption that
loopback binding is enough and the server lives "for a few seconds". It actually lives for the whole
unlocked session, and loopback is reachable from the user's browser.

*Evidence (reproduced):* against a child launched with the app's exact flags, a request a web page can
send without a CORS preflight — `POST /json_rpc`, `Content-Type: text/plain`, `Host: evil.example` —
executed `create_wallet` and then **`query_key` returned the 25-word seed**. The server does not check
`Host` (DNS rebinding can read responses) and processes `text/plain` bodies (blind CSRF of `transfer` /
`sweep_all` works without reading anything). Any local process or user could drive it too.

*Fix:* per-session random HTTP Digest credentials. They are passed through a `0600` `--config-file`
inside a `0700` session directory, not argv, which other users can read via `/proc/<pid>/cmdline`, and
shredded once the server is up. The client sends credentials only for the `Digest` scheme, never Basic,
and never through a system proxy. The code's reason for disabling login ("digest + POST body can't
replay") was tested and is false on .NET 8: three consecutive digest-authenticated POSTs returned 200.
*Verified by:* `Backend_Rejects_Unauthenticated_And_Cross_Origin_Requests` (that exact request now
gets 401); `Session_Artifacts_Stay_Inside_The_Shredded_Directory` (no password in argv, dir mode 0700).

### XW-02
**Critical — the decoy's own payload proves a hidden wallet exists.**
The JSON sealed in each slot carried `"kind"` (`0` real / `1` duress), a label (`"Main"` vs
`"Wallet"`) and `"duressWipeReal"`. The duress feature exists for the case where an adversary holds the
device **and** the duress password. The vault format is public, so decrypting the decoy slot and reading
`"kind":1` is a few lines of code. README's "no flags, no metadata" was not true.

*Fix:* payload v2 — one identical field set for every slot (`v, network, mnemonic, seedOffset,
restoreHeight, daemonAddress, ephemeralWalletPassword, wipeOther`), no kind, no label. `WalletSecrets`
and `UnlockResult` no longer carry a real/decoy notion at all. v1 slots still open and are re-sealed as
v2 the first time their password is used (a slot can only be migrated with its own password; see
XW-22 for what that means for existing decoys).
*Verified by:* `DeniabilityTests` — decrypts slots exactly as an examiner would and asserts the decoy's
field list equals a single-wallet vault's; legacy-migration tests use byte-for-byte v1 payloads.

### XW-03
**High — "Change password" announced the real wallet.**
After unlocking with the duress password, Settings → Change password with that same password replied
*"That current password didn't unlock the real wallet."* — on screen, to whoever is coercing.

*Fix:* `ChangePassword` is now symmetric, like change-node: it re-seals whichever slot the password
opens, with neutral wording. It still refuses a new password that would open the other slot.
*Verified by:* `ChangePassword_Is_Symmetric_And_Only_Touches_The_Opened_Slot`.

### XW-04
**High — the send amount depended on the OS locale.**
The amount box was bound to a `decimal`, converted with the current culture, which accepts the group
separator. Reproduced in a headless Avalonia 11.1.3 harness: **en-US `0,25` → 25 XMR, `1,5` → 15 XMR;
de-DE `0.5` → 5 XMR; fr-FR `0.5` → 0**. The confirm dialog showed the wrong amount, which is the
only thing between a typo and an irreversible over-send.

*Fix:* `XmrAmount.TryParse`. `.` or `,` is always the decimal point and never a thousands separator,
so ambiguous input can only parse *lower* than intended. Live read-back (`= 0.25 XMR`) flags
thousands-looking input, and all amounts display culture-invariantly.
*Verified by:* `XmrAmountTests` (the exact inputs above, under six cultures).

### XW-05
**High — generated wallets rescanned the whole chain on every unlock.**
A generated seed's restore height came from wallet-rpc's `get_height` immediately after
`create_wallet`. That reports the wallet's local chain, which is **1**, not the tip; reproduced with
the tip at 301. Because the app restores from seed on every unlock, every unlock of a "new" wallet
scanned from genesis. That's slow on test networks and hours on mainnet through a remote node. README
claimed "first sync is fast".

*Fix:* read the **daemon's** tip *before* the seed exists, minus a 720-block margin (0 = full scan if
the node is unreachable). The same margin applies to "scan from now". (XW-24 then caps the node's
claim by the clock.)
*Verified by:* `Generated_Seed_Restore_Height_Tracks_The_Daemon_Tip` (against a chain grown past the margin).

### XW-06
**High — wipe-on-duress left the real wallet on the device.**
Settings → Restore keeps the replaced vault as `vault.xv.replaced-<time>` ("never destroyed"). A
duress wipe overwrote only `vault.xv`, so the real slot survived in those copies, contrary to the
"permanently, on that device" promise.

*Fix:* a wipe now also shreds `vault.xv.replaced-*`. The wipe fires on **any** use of the duress
password (unlock, change password, change node), and the survivor is re-sealed with the flag cleared
using the key already derived. So a duress unlock costs no extra Argon2 time and leaves a vault that
looks like a single-wallet one.
*Verified by:* `Duress_Wipe_Destroys_Replaced_Vault_Copies_Left_By_Restore`,
`Wipe_Fires_When_The_Duress_Password_Is_Used_To_Change_A_Password` (and `…_Change_The_Node`),
`Wipe_Reseals_With_The_Already_Derived_Key`.

### XW-07
**Medium — History showed 0 XMR for every transaction.**
`DataGridTextColumn` bindings are TwoWay. With the one-way XMR converter, `ConvertBack` threw on every
row (8 binding errors in the smoke test) and the cells rendered `0`.
*Fix:* a purpose-built history list (`HistoryRow`) with plain one-way display strings.
*Verified by:* the UI smoke test, which now fails on any binding error.

### XW-08
**Medium — addresses could display differently from their text.**
`SelectableTextBlock` didn't match the `TextBlock.mono` style, so addresses fell back to Inter, whose
contextual alternates render an `x` between digits as `×` (`…BUP2x2Uim…` displayed as `2×2`). The
same happened in the original app wherever an address used the default font.
*Fix:* `:is(TextBlock).mono` covers every address, txid and key, which render in Cascadia Mono or Consolas.
*Verified by:* rendered output inspected; the QR round-trip check decodes the Receive QR and requires
it to equal the displayed address URI.

### XW-09
**Medium — wallet-rpc wrote persistent files outside the shredded directory.**
With no `--log-file`, wallet-rpc wrote `monero-wallet-rpc.log` to the process working directory. Every
seed restore adds a ~280-line timestamped burst, so vault creation with an imported real and decoy seed
leaves two bursts seconds apart. It also created `~/.shared-ringdb`, which grew from 12 KB to 36 KB on
a single send. Both outlived lock, exit and duress wipe.
*Fix:* `--log-file` and `--shared-ringdb-dir` inside the session directory; `WorkingDirectory` set there too.
*Verified by:* `Session_Artifacts_Stay_Inside_The_Shredded_Directory`.

### XW-10
**Medium — the app's own log could tell the wallets apart.**
`xaultwallet.log` persists and survives a wipe. It recorded `"syncing against <node> from height <N>"`
on every unlock (the restore height is unique per seed) and "Transfer submitted" on every send, which
can be checked against the decoy's on-chain history. RPC exception messages, which are logged, also
embedded the (redacted) request body, including restore heights and destination addresses.
*Fix:* those lines are removed. Exception messages carry only the method and the backend's error;
the redacted body moves to `MoneroRpcException.Diagnostics`, which is never logged.

### XW-11
**Medium — "Fetch key from wallet" never worked.**
`get_tx_key` answers `{"tx_key": …}`, but the code read it through the `{"key": …}` DTO used by
`query_key`, so every lookup produced an empty key with no error. *Found by the new integration test.*
*Fix:* a dedicated `GetTxKeyResult`, and an empty key now throws. *Verified by:* the regtest funds-flow test.

### XW-12
**Medium — port-hijack race.**
The child's port is chosen, released, then passed on its command line, which other users can read. A
process that binds it first makes the child fail to bind and receives `restore_deterministic_wallet`,
seed included. Digest auth doesn't help: it authenticates only the client, and monero sends no `rspauth`.
*Fix:* before any secret is sent, verify that every listener on the port belongs to the child: `/proc`
on Linux, `GetExtendedTcpTable` on Windows. A 401 during readiness is now a hard failure.
*Residual:* macOS has no equivalent check here; there the risk is the pre-existing one.
*Verified by:* `LoopbackPortOwnershipTests` (own listener, foreign PID, closed port). **The first version
of this fix failed open; see XW-21.**

### XW-13
**Medium — mainnet by default.** First-run defaults were mainnet and `127.0.0.1:18081` in an app whose
README says not to use real funds. *Fix:* Stagenet by default; mainnet stays one click away behind its
red warning (now also a red "MAINNET · REAL FUNDS" pill on the wallet screen).

### XW-14
**Low — PATH auto-detect.** A blank binary path fell back to the bare name `monero-wallet-rpc`, but the
launcher requires `File.Exists`, which is false for bare names. "Test binary" (via `Process.Start`) passed
while unlocking failed. *Fix:* `ExecutableLocator` resolves PATH to an absolute path and skips relative
PATH entries. *Verified by:* `ExecutableLocatorTests`. (XW-25 closes the remaining relative-path case.)

### XW-15
**Low — guessable passwords.** Only "8+ characters" was enforced; `password`, `12345678`,
`Password123!` and `qwertyuiop` were accepted for a file that can be attacked offline. *Fix:* the estimator
discounts repeats, sequences, keyboard runs and the most common passwords, and *Very weak* is refused
for main, duress and changed passwords. Still a heuristic; zxcvbn would be better.

### XW-16
**Low — redaction gaps.** `sweep_all`'s `tx_key_list` / `tx_metadata_list` (and other `*_list` /
txset fields) weren't redacted, and the stderr tail, which reaches exceptions and the log, wasn't
scrubbed. *Fix:* keys added, and the stderr tail masks address-length base58 and 64-hex strings.

### XW-17
**Low — the bundled font was never used.** The window asked for the family name `Inter` (a system
lookup), so Linux fell back to DejaVu. *Fix:* reference the embedded `fonts:Inter#Inter`.

### XW-18
**Low — restore height input.** The import "specific block" box was a culture-bound `ulong`; `2.800.000`
on de-DE failed to bind and silently left 0. *Fix:* `BlockHeight.TryParse`, culture-independent.
(The first version accepted *any* grouping; see XW-26.)

### XW-19
**Low — silent second launch.** A second instance exited with code 2 and no feedback. *Fix:* on
Windows it signals the running instance, which restores and focuses its window.

### XW-20
**Info — daemon probe route.** Without a SOCKS proxy the app's own daemon probe used the system or
environment proxy, while wallet-rpc connects directly. *Fix:* the probe takes wallet-rpc's route.

## Second pass

An independent adversarial review of the first-pass fixes, re-verified the same way.

### XW-21
**High — the port-ownership check failed open.**
XW-12's check returned *"can't tell"* whenever reading the tables threw, and *"can't tell"* was
treated as *"fine"*. In the hijack, the child loses the port and **exits**. Once it is reaped, its
`/proc/<pid>/fd` is gone, enumeration throws, and the check passes. An impostor that answers at once was
refused, because the child was still alive. An impostor that simply **holds its first answer until the
child is gone** was not. Reproduced against the pre-fix commit (`bad2684`): that impostor received
`get_version`, then `restore_deterministic_wallet` carrying the `seed` and the wallet password.
Two smaller gaps: the check didn't run before `create_wallet`, so an impostor could hand out a seed it
knows. And on Windows, a same-port listener on an unrelated interface made the check refuse a
legitimate backend.
*Fix:* fail closed. A vanished process owns nothing, and on Linux/Windows only a definite *yes* passes
(`LoopbackPortOwnership.IsTrusted`). `MoneroProcessManager.EnsureBackendIsOurs()` also requires the child
to be alive, and runs at readiness, before `restore_deterministic_wallet` and before `create_wallet`.
Windows only considers `127.0.0.1` and wildcard listeners.
*Verified by:* `A_Process_That_Has_Exited_Owns_Nothing`, `Only_A_Definite_Yes_Is_Trusted…`, and the
regtest test `Seed_Is_Never_Sent_To_An_Impostor_Holding_The_Backend_Port`. That test binds the port
before the real `monero-wallet-rpc` and answers like a server, in two variants. The prompt impostor is
refused with *"Another program is answering…"*. The patient one is refused with *"monero-wallet-rpc is
not running"*. Both stop after one `get_version`, and neither ever receives the seed. Run unchanged
against `bad2684`, the patient variant fails as described above.

### XW-22
**Medium — upgraded 0.1 vaults keep the decoy marker until the decoy is used.**
A slot can only be re-sealed by its own password. After a 0.1 user unlocks with the main password, the
decoy slot still holds `"kind":1` inside its encryption, which is XW-02's leak. Using the duress password
converts it, but with 0.1's wipe-on-duress enabled it also wipes the main wallet. Nothing told the user any of this.
*Fix (mitigation, the format can't be fixed from the other slot):* `UnlockResult.UpgradedFromLegacyFormat`
triggers a one-time notice. It is deliberately **symmetric**: it is shown for *either* slot of a 0.1 vault.
A notice only for 0.1 "main" slots would make the first decoy unlock after upgrading look different.
`SECURITY.md` → *Upgrading from 0.1* explains the exposure and gives a rebuild procedure.
*Verified by:* `Upgrade_Is_Reported_Once_And_Identically_For_Either_Slot` (both slots, true then false),
`A_Current_Format_Vault_Never_Reports_An_Upgrade`, and the `wallet-upgraded` UI snapshot.

### XW-23
**Medium — files created world-readable.**
Everything was written with the process umask. With the common `022`, that means `0644` files in a
`0755` folder: the vault (offline-attackable), the logs and, worst, the optional **plaintext seed
backup**. Whether another account could actually read them came down to the permissions of the parent
folders. The app relied on those instead of setting its own.
*Fix:* `PrivateFiles`. The data and log folders are `0700`, and the vault, settings, logs, temp files,
restored vaults and exports are `0600`. Files are created with that mode, and an existing file is
tightened *before* anything is written into it. At startup, folders made by older versions are swept
(symlinks are neither followed nor changed). Save-dialog files (seed backup, history CSV) are written
by the app as `0600` whenever the dialog yields a local path. Windows relies on the profile ACLs.
*Verified by:* `PrivateFilesTests` under umask `022`, including the real vault write and the logger.

### XW-24
**Medium — a node's height became a new seed's restore height unchecked.**
XW-05 made a new seed start at the node's tip minus 720 blocks. A lying or broken node claiming a
far-future height pushed that start above the real chain. The height is sealed in the vault, so the
payments that followed would stay invisible even after switching to an honest node.
*Fix:* `RestoreHeights.ForNewSeed` takes `min(node tip, clock estimate) − 720`. The estimate is
monero's own `wallet2::get_approximate_blockchain_height`, ported from upstream `master` (latest hard
fork's height and time, 120 s per block, minus a per-network correction). Taking the lower value can
only cost extra scanning.
*Verified by:* `RestoreHeightTests` (upstream values hand-computed for all three networks, a 99,999,999
claim capped, regtest-sized chains passed through) and `Generated_Seed_Restore_Height_Tracks_The_Daemon_Tip`.
*Residual:* if the estimate itself runs ahead of the real chain, a lying node can still push the start
past the tip by that lead minus 720 blocks.

### XW-25
**Low — a relative binary path could run a file from the current directory.**
The launcher accepted any path for which `File.Exists` was true, and `File.Exists` resolves relative
names against the current directory. `Process.Start` then searches the app's folder, the current
directory and `PATH`. A bare name in Settings, or the old fallback when auto-detect found nothing, could
therefore start a planted `monero-wallet-rpc` from wherever the app was launched, and that process
receives the seed.
*Fix:* `ExecutableLocator.EnsureLaunchable` refuses anything not fully qualified, in both the launcher
and "Test binary". Bare names typed in Settings resolve on `PATH` (`ResolveConfigured`). Auto-detect
returns *nothing found* instead of a bare name.
*Verified by:* `A_Relative_Name_Is_Never_Launched_Even_When_The_File_Is_Right_There` (the planted file
exists in the current directory) and the `ResolveConfigured` tests.

### XW-26
**Low — height parsing too lenient.**
XW-18's parser stripped every separator, so `3150000.0` became **31,500,000**, and `31,50,000` or
`3,150.000` were accepted. A restore height that's too high hides payments.
*Fix:* plain digits, or groups of exactly three behind one kind of separator. Everything else is refused.
*Verified by:* `BlockHeightTests` (the inputs above, plus `3'150'000` and `1,000` still accepted).

### XW-27
**Low — history row stuck at "9/10 confirmations".**
To keep the scroll position, history redraws only while a row is still confirming. That was judged at
the *new* height, so the block that settles a row was exactly the one that skipped the redraw.
*Fix:* judge at the old height (`OnHeightChanged(oldValue, newValue)`).
*Verified by:* the UI smoke test's history check (9 → 10 confirmations must redraw as settled). It fails
with the old condition.

### XW-28
**Low — key material left un-zeroed on a failure path.**
`VaultFile.TryOpen` derives a key for both slots. If slot 0 opened and slot 1's Argon2 derivation then
threw (e.g. out of memory), the opened payload and its key escaped every `using` block. `TryDecrypt` also
ran outside the `try`, so a throw there leaked that key.
*Fix:* everything for a slot runs inside its `try`, and a failure disposes an already-opened result.
*Not separately tested:* it would need fault injection into the KDF. The change is structural and
covered by the existing open/unlock tests.

### XW-29
**Info — `1,000 XMR` skipped the read-back hint.**
`TryParse` accepted the `XMR` suffix but `LooksThousandsGrouped` didn't, so that input showed no
*"did you mean thousands?"* note. *Fix:* same suffix handling. *Verified by:* `XmrAmountTests`.

## Residual risks (documented, not fixed)

- **Wipe flag before it fires.** An examiner who decrypts the decoy *offline*, without the app ever
  opening it, can see `wipeOther: true` and infer a second wallet. That's inherent: the instruction must
  be readable with the duress password. Without wipe-on-duress, the decoy is indistinguishable.
- **Multiple snapshots of the vault file** taken over time reveal which slots changed. If both changed,
  two live wallets exist. This is the same limitation as hidden volumes.
- **Every unlock rescans from the restore height.** Only the seed persists, which is a design choice.
  Old wallets on mainnet will sync slowly on every unlock. Advancing the stored height past spent
  history, or an opt-in encrypted cache, would fix it at a privacy cost.
- **Managed memory and SSD shredding** remain best-effort (unchanged; see SECURITY.md).
- **macOS:** no port-ownership check (XW-12/XW-21); the per-session digest credentials remain.
- **0.1 vaults and their copies** keep the decoy marker until the decoy is used or the vault is rebuilt
  (XW-22). Copies made before upgrading keep it forever.
- **Restore-height cap** is only as good as the clock estimate (XW-24).
- **Release binaries are unsigned.** The release workflow publishes SHA256SUMS; code signing needs a certificate.
- **No independent audit yet** of the vault format or of the Konscious Argon2 implementation.

## Recommendations, in priority order

1. Commission the professional third-party audit before any mainnet story, as the README already says.
2. Sign release binaries (Authenticode, Apple notarisation) and pursue reproducible builds.
3. Restore-height advancement (or an opt-in encrypted wallet cache) to make old wallets unlock fast.
4. Exclude the window from screen capture while the seed is shown (`SetWindowDisplayAffinity`).
5. Replace the strength heuristic with zxcvbn, and add an optional keyfile second factor.
6. Built-in Tor (`--proxy` + `.onion` nodes) with a clear UI toggle, since the SOCKS plumbing already exists.
